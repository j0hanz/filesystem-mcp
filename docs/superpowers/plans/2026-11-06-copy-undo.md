# Copy Undo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `move` call with `copy: true` returns an undo id, and `undo` removes what the copy created and puts back the files it overwrote.

**Architecture:** Before the copy, `#copy` in `src/core/fs.ts` walks the source tree. For each entry it records what the destination counterpart was: absent, an existing directory, or an existing file (whose bytes are saved with `saveOld`). After the copy it hashes each new or replaced file and pushes the existing record types: `remove` for a new file, `write` for a replaced file, and `rmdir` for a new directory. No new record op, no restore change. The capture is per path through `#forMutation(validDest, …)`, the way `rm` and `#move` do it, so one copy that cannot be undone no longer costs the whole call its undo.

**Tech Stack:** TypeScript on Node, `node:test`, existing `UndoCapture` / `restoreEntry` in `src/core/undo.ts`.

**Spec:** `PONYTAIL-DEBT.md` entry for `src/core/fs.ts:1099`: "`copyFile` abandons undo capture instead of tracking new vs. overwritten entries across a merged tree. upgrade: snapshot destination entries before `fsCp` the way `snapshotTree` does."

## Global Constraints

- No new `UndoRecord` op and no change to `restoreEntry`, `restoreOrder` or `UndoPreview`.
- Saved bytes draw on the existing capture budget through `saveOld` (`capture.reserve`). The budget stays as it is.
- A sensitive destination entry is refused like in `snapshotTree`: `capture.abandon('contains protected files')`.
- Cross-device moves (`#moveAcrossDevices`) keep abandoning. Only `op === 'copy'` changes.
- Do not hand-edit versions in `package.json`, `server.json` or the plugin manifests.
- After the code changes, run `graphify update .`.

## Review Focus

1. A merge copy that fails part-way: expect no undo id for that path. The plan refuses the foreseeable case, a different kind of entry, first (test in Task 1). The `the copy failed part-way` catch covers I/O errors, and no test can inject one: `RawOps` has no `cp`.
2. A copied file that the user edits before running undo: restore refuses that file and still restores the others (test in Task 1).
3. A copy that overwrites a protected file such as `.env`: expect no undo for that path, no saved bytes held (test in Task 1).
4. A copy over a file larger than the budget: expect `too large to keep for undo`, and the copy still lands (test in Task 1).
5. A large tree copy hashes every copied file a second time. This costs a second full read of every copied file, and no test covers it. Note it in the PR.

- [ ] **Step 3: Implement `planCopyUndo` in `src/core/undo.ts`**

Walk the source in pre-order with `fsLstat(…, { bigint: true })` on each source entry and its destination counterpart (`unlessMissing` for absent):

- If the destination is sensitive (`fs.pathGuard.isSensitive`): `abandon('contains protected files')`.
- If the source is a file and the destination is absent: push a `new-file` target.
- If the source is a file and the destination is a file: call `saveOld`, then push a `replaced-file` target. When it returns `undefined`, stop: `saveOld` has already abandoned.
- If the source is a directory and the destination is absent: push a `new-dir` target, then recurse. Every child is then absent.
- If the source is a directory and the destination is a directory: recurse, no target.
- If the source is a symlink: `abandon('copied links are not undoable')` with `// shortcut: no record removes a link a call created; add one if clients copy trees with links`.
- A source file or directory whose destination exists as another kind: `abandon('a copy would replace a different kind of entry')`.
- Any other source (FIFO, socket, device): `abandon('cannot capture a non-regular entry')`.
- When any read throws: `abandon('could not read the copy destination')`.

Return `[]` when abandoned. Check `capture.unavailableReason()` after each child, as `snapshotTree` does.

- [ ] **Step 4: Implement `recordCopyUndo` in `src/core/undo.ts`.** Export `hashFile`. Walk `targets` in order:

- `new-file`: push `{ op: 'remove', path, expect: await hashFile(fs, path) }`.
- `replaced-file`: push `{ op: 'write', path, ...saved, expect: await hashFile(fs, path) }`.
- `new-dir`: push `{ op: 'rmdir', path }`.

When a hash throws: `abandon('could not read the copied files')`. `restoreOrder` already reverses the records and runs `rmdir` last, deepest first.

- [ ] **Step 5: Wire `#copy` in `src/core/fs.ts:1093`**

Delete `this.#capture?.abandon('copies are not undoable yet')` and its `ponytail:` comment. Wrap the three existing branches in `this.#forMutation(validDest, async (own) => { … })`:

1. `const targets = own.recording ? await planCopyUndo(own, this, validSource, validDest) : [];`
2. Run the existing branch (`#copyIntoPlace` / `#copyMerging` / `fsCp`) unchanged, awaited, inside `try`.
3. On `catch`: `own.abandon('the copy failed part-way'); own.changed(); throw error;`
4. After success: `if (own.recording) await recordCopyUndo(own, this, targets); own.changed();`
